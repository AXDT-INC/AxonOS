# Off-server CAPI image preparation

This recipe supersedes the earlier PASSWORD build-argument recipe. Build the exact reviewed release commit. Synthetic validation images are not
authorized production images. The validated build corrections are reconciled: scientific dependency installation
has a 30-minute bound, Kubo v0.24.0 uses bounded HTTPS and a pinned SHA-512,
and synthetic prefix-cache reuse requires a fresh credential-layer nonce.
Source readiness does not authorize production builds or deployment.
The previous repository tests remain historical evidence for unchanged CAPI code.

## Credential handling

Both password-consuming RUN instructions require the axonos_password BuildKit
secret, and reject an empty file. There is no ARG PASSWORD or Compose PASSWORD
build argument. The account name, chpasswd, vncpasswd -f, permissions and runtime
authentication paths are preserved. The input is a nonempty single value without
newline, matching the former environment value; the commands append a newline.
No secret value is placed in command arguments, labels or build provenance.

The image STILL contains /etc/shadow password hashes and the VNC password file;
images and their cache remain credential-sensitive. BuildKit secret mounts do
not make these outputs credential-free. Retain them only on an authorized host.
By default the recipe uses --no-cache for BOTH builds, preventing reuse of old credential
layers and ensuring missing required secrets cannot be hidden by a cache hit.
BuildKit secret contents are not cache invalidators.
Build caches are not deleted; a dedicated builder must have isolated storage and
an approved GC policy that cannot remove production images/caches.

For explicitly authorized synthetic-only validation, the optional selector
AXONOS_SYNTHETIC_PREFIX_CACHE=yes permits gate cache reuse before credentials.
The recipe generates a fresh independent 256-bit non-secret
AXONOS_CREDENTIAL_CACHE_NONCE internally on every invocation. Both required
secret-consuming RUN instructions reference it and reject a missing/empty nonce.
Changing it invalidates the account step and every downstream layer, including
VNC; the nonce is public metadata, never a password or password hash.
The worker retains --no-cache. The normal path retains --no-cache for both images.
Only unchanged layers before the first credential step may be reused. Because
scientific installations follow that step, they must rebuild; this exception
does not authorize reusing password-derived layers or restructuring the image.
The external synthetic supervisor must reject a cache hit on either secret step
and retain the existing CPU, memory, PID, disk and wall-time safeguards. This
exception does not authorize production builds or credential export.

A synthetic-secret image contains no production credentials but is NOT literally
credential-free: it embeds synthetic account/VNC credentials. It is for isolated
validation only. Retagging it cannot provision production authentication.
A production-authentication image requires a separately authorized no-cache
rebuild using the existing password delivered by an approved secret custodian.
Do not copy the production .env to the workstation. Do not rotate credentials.
Runtime secret provisioning would require startup/authentication changes and a
separate review; none are implemented here. Required secret mounts alone cannot
remove password-derived files intentionally generated by these RUN instructions.

Existing production controller and scripts/build_axonos.sh are NOT the authorized
build path for this commit: they do not supply the required secret. The Compose
PASSWORD argument has been removed, but no production configuration was changed.
There is no fallback password. The off-server script never invokes Compose,
initializers, migration scripts, push, prune, tag promotion or service replacement.

## Host and builder prerequisites

The build host must be verified independently for each build. Obtain operator evidence of Linux amd64, Docker/Buildx with secret-mount
support, and sufficient free dedicated disk and RAM. Use native amd64 for this
CUDA/scientific stack; do not assume an ARM workstation/emulation is equivalent.
No GPU is needed merely to compile; NVIDIA/GPU runtime validation requires a
separately suitable host and is not claimed by this preparation.

Use an ALREADY approved dedicated builder on the off-server machine. Verify its
endpoint is not clu1; client Docker context must also be off-server, since --load
imports into the selected client daemon. The hostname guard is only an extra
check, not an endpoint authorization mechanism. Do not select the default
production builder. The approval environment variable is an operator assertion,
not a measurement of resource isolation.

Approve and record hard CPU/cpuset, memory/swap, PID and backing-filesystem quota
limits, isolated cache ownership, and minimum remaining host/storage headroom.
Proposed starting envelope: 8 visible CPUs, 32 GiB RAM, no additional swap,
1024 PIDs, 250 GiB dedicated builder storage with at least 50 GiB reserve;
these are planning bounds, not measured build requirements. Full scientific
compilation can exceed them and must fail rather than silently lift limits.
CPU quota alone may not constrain nproc; verify CPU visibility/affinity within
the builder's execution environment. Build one image at a time. No other writer
may use this run's random tags. Build timeout does not guarantee immediate
remote cancellation; operator must verify builder idleness after interruption.
Account for the separate Docker destination image store as well as builder cache.
No builder provisioning or resource modification is performed by this recipe.

## Inputs and provenance

Gate: repository root Dockerfile/context; AXONOS_SKIP_HEAVY=0; exact approved
NVIDIA_DRIVER_PKG_VERSION; required secret; reviewed linux/amd64 digest for
nvidia/cuda:12.2.2-cudnn8-devel-ubuntu22.04 supplied as AXONOS_GATE_BASE.
Worker: same context, docker/x-capi-worker/Dockerfile; existing digest-pinned
Python base; no password secret. The gate base default remains source-compatible,
but this recipe refuses a mutable base reference.

Review the CUDA digest against the intended tag/platform before approving it.
The Dockerfile frontend, package repositories and other downloaded dependencies
are not all immutable; these builds are NOT claimed bit-reproducible. Commit,
Dockerfile hashes, base digest, driver version, unique tags and resulting local
image IDs are emitted. Local image IDs are not registry manifest digests.
Retain the sanitized output as build evidence. No automatic publication occurs.

## Exact build-only invocation, after separate host/secret approval

Set these non-secret selectors and a path to an owner-only secret file OUTSIDE
the checkout. For the first validation build that file must contain synthetic
input, never a production credential. Do not paste its contents into commands.
Use a clean checkout of the final reviewed commit and run:

```sh
AXONOS_OFF_SERVER_BUILD_APPROVED=yes \
AXONOS_BUILD_REVISION='<full reviewed commit>' \
AXONOS_BUILD_BUILDER='<approved off-server builder>' \
AXONOS_GATE_BASE='nvidia/cuda@sha256:<reviewed amd64 digest>' \
NVIDIA_DRIVER_PKG_VERSION='<approved exact package version>' \
AXONOS_BUILD_PASSWORD_FILE='/absolute/owner-only/synthetic-secret' \
python3 -I -B scripts/build_capi_off_server.py
```

No build is authorized by this document. First obtain build-host/builder evidence,
base digest and driver version, then approve synthetic-secret validation. No
production credential export is needed for that step. Missing secret behavior
is source-validated here, not claimed as an executed BuildKit integration test.
Backup freshness, schema4 attestation, migration008, generation recovery and
renter continuity remain separate production prerequisites. Keep CAPI/handoff off.
